## 3. Что здесь вообще происходит — понятное объяснение

### 3.1. Что делает диффузионная модель

При обучении диффузионной модели к настоящему изображению добавляют шум. Нейросеть получает зашумлённую картинку и информацию о силе шума, после чего учится оценивать шумовую составляющую.

При генерации процесс начинается со случайного массива чисел. Далее нейросеть многократно помогает перейти к состоянию с меньшим шумом. В результате появляется изображение.

В нашем проекте обучение уже выполнено авторами готовых весов. Мы исследуем **способ последующей генерации**. В частности, DDIM позволяет использовать модель с тем же обучающим заданием для другого процесса получения изображений. [arxiv.org](https://arxiv.org/abs/2010.02502?utm_source=chatgpt.com)

Здесь нужно различать три понятия.

| Понятие | Что оно означает | Пример вопроса |
|---|---|---|
| **Модель** | Нейросеть, оценивающая шум по текущей картинке и уровню зашумления | «Что сейчас следует считать шумом?» |
| **Сэмплер** | Алгоритм, который использует предсказание модели и вычисляет следующее состояние | «Как сделать следующий переход?» |
| **Расписание** | Последовательность уровней шума, через которые проходит генерация | «Какие промежуточные состояния посетить?» |

В проекте используется одна модель, но меняются сэмплер и расписание.

### 3.2. Почему вообще можно ускорить генерацию

Представь, что изображение получается за 1000 небольших переходов. Каждый переход требует вычислить нейросеть.

Можно попробовать выполнить 20 более крупных переходов. Это сократит число обращений к модели, но увеличит ошибку: алгоритм будет сильнее «перепрыгивать» между состояниями.

Возникают два вопроса:

1. Как вычислять крупный переход, чтобы меньше терять в качестве?
2. Где расположить промежуточные уровни, если число обращений к модели ограничено?

Первый вопрос исследуется сравнением сэмплеров. Второй — подбором расписания.

### 3.3. Как работает DDIM

DDIM удобно реализовать первым.

Один его переход можно описать так:

1. Передать текущее зашумлённое изображение в модель.
2. Получить оценку шума.
3. Вычислить оценку чистого изображения.
4. Использовать её для перехода к следующему, меньшему уровню шума.

Для проекта выбираем **`eta=0`**. В этом режиме DDIM не добавляет новый случайный шум в процессе генерации. При фиксированных модели, начальном состоянии и расписании получается детерминированная траектория. Один переход требует одного нового вызова модели. [Hugging Face](https://huggingface.co/docs/diffusers/api/schedulers/ddim?utm_source=chatgpt.com)

В упрощённых обозначениях зашумлённое изображение имеет вид

\[
x_t=a_t x_0+b_t\varepsilon.
\]

Здесь \(a_t\) и \(b_t\) — известные коэффициенты, определяющие доли сигнала и шума. Если модель предсказала \(\widehat\varepsilon_t\), можно получить оценку чистого изображения:

\[
\widehat x_0=\frac{x_t-b_t\widehat\varepsilon_t}{a_t}.
\]

После этого DDIM строит следующее состояние с другими коэффициентами зашумления. Эта последовательность непосредственно связывает формулу с программной реализацией. [arxiv.org](https://arxiv.org/html/2010.02502v4?utm_source=chatgpt.com)

### 3.4. Чем отличается DPM-Solver++ второго порядка

В этой теме нужен **многошаговый вариант второго порядка**, обычно обозначаемый **DPM-Solver++ 2M**.

Он использует:

- текущую оценку чистого изображения;
- сохранённую оценку с предыдущего шага;
- информацию о величине соседних переходов.

За счёт предыдущего ответа алгоритм учитывает, как меняется предсказание по траектории. При этом второй порядок **не означает два новых вызова нейросети на каждом шаге**: предыдущий ответ уже сохранён.

Первый переход выполняется по формуле первого порядка, поскольку истории ещё нет. Для неравномерного расписания коэффициенты должны учитывать фактические интервалы между уровнями. [arxiv.org](https://arxiv.org/abs/2211.01095?utm_source=chatgpt.com)

Для проверки используется `DPMSolverMultistepScheduler` с настройками:

- `algorithm_type="dpmsolver++"`;
- `solver_order=2`;
- `solver_type="midpoint"`.

Параметры начальных и завершающих переходов тоже должны совпадать у собственной и библиотечной реализаций. [Hugging Face](https://huggingface.co/docs/diffusers/api/schedulers/multistep_dpm_solver?utm_source=chatgpt.com)

### 3.5. Чем отличается Heun

Heun сначала делает предварительный переход, затем уточняет его:

1. Вычисляет направление изменения в текущей точке.
2. Делает предварительный шаг.
3. Снова вызывает модель в предварительно полученной точке.
4. Использует оба направления для окончательного перехода.

На большинстве переходов получаются **два вызова нейросети**. Последний переход к нулевому шуму выполняется без второго вызова, по методу Эйлера. Для детерминированного варианта EDM дополнительное случайное возмущение отключается через `S_churn=0`. [GitHub](https://github.com/NVlabs/edm/blob/main/generate.py?utm_source=chatgpt.com)

Для проверки на выбранной DDPM-модели подходит **`HeunDiscreteScheduler`**. Его документация прямо указывает связь с алгоритмом Heun из EDM. [Hugging Face](https://huggingface.co/docs/diffusers/api/schedulers/heun?utm_source=chatgpt.com)

### 3.6. Где находится основная техническая сложность

Три алгоритма должны одинаково понимать вход и выход модели.

DDPM работает с нормированным зашумлённым изображением и меткой обучающего времени. В схеме EDM удобно использовать другой масштаб изображения и уровень шума \(\sigma\). Поэтому потребуется небольшой адаптер, который:

- переводит уровень шума в нужную временную метку;
- правильно масштабирует вход;
- преобразует предсказание шума в оценку чистого изображения.

Это несколько математических преобразований вокруг готового U-Net. Формулы адаптера включены в документ.

Параметры шума нужно брать из конфигурации модели. Для `google/ddpm-cifar10-32` там указаны 1000 обучающих временных меток, линейные beta от 0,0001 до 0,02 и включённый `clip_sample`. Подстановка параметров другого scheduler по умолчанию может сделать сравнение некорректным. [google/ddpm-cifar10-32 at main](https://huggingface.co/google/ddpm-cifar10-32/blob/main/scheduler_config.json?utm_source=chatgpt.com)

**Для первой реализации предлагаю выбирать уровни только из исходной таблицы модели.** Это позволит сначала обойтись без отдельного исследования непрерывной интерполяции времени.

## 4. В чём будет собственная исследовательская работа

Одного воспроизведения трёх алгоритмов недостаточно: в задании предусмотрен подбор расписания.

### 4.1. Что именно будем улучшать

Допустим, на одну генерацию выделено 19 вызовов модели. Нужно определить, какие уровни шума стоит посетить за этот бюджет.

Сначала используются два стандартных варианта:

- равномерное расположение по исходному времени модели;
- расписание Karras, привязанное к доступным уровням DDPM.

Расписание Karras задаёт неравномерное распределение уровней; его схема и реализация представлены в работе EDM и авторском коде. [arxiv.org](https://arxiv.org/abs/2206.00364?utm_source=chatgpt.com)

Затем проверяем гипотезу:

**Можно ли уменьшить ошибку короткой генерации, изменив расположение нескольких промежуточных уровней и сохранив число вызовов модели?**

Начальный и конечный положительный уровни нужно зафиксировать. Иначе одновременно изменятся и распределение переходов, и диапазон генерации.

### 4.2. Откуда брать изображение для сравнения

Для каждого начального шума один раз получаем результат длинной детерминированной генерации.

Практический вариант — **DDIM с `eta=0` и 1000 вызовами модели**. Полученную картинку сохраняем. Затем запускаем короткую генерацию из того же начального состояния и сравниваем результаты.

Здесь есть существенный смысловой момент: **опорная картинка получена самой моделью**. Она не является настоящим изображением CIFAR-10, которое «соответствовало» случайному шуму. В безусловной генерации такой известной пары нет.

Перед массовым использованием опорных результатов нужно проверить их устойчивость. На небольшой группе шумов сравнить длинные генерации с 250, 500 и 1000 вызовами при одинаковых границах. Желательно также сопоставить с достаточно плотной генерацией другим детерминированным методом.

Если длинные решения заметно расходятся, MSE следует интерпретировать осторожно: как близость к конкретному выбранному ориентиру.

### 4.3. Как измерять ошибку

Для подбора используем среднюю квадратичную ошибку:

\[
L(S)=\frac{1}{mCHW}
\sum_{j=1}^{m}
\left\|G_S(z_j)-G_{\mathrm{ref}}(z_j)\right\|_2^2.
\]

Здесь:

- \(S\) — проверяемое расписание;
- \(z_j\) — начальный шум;
- \(G_S(z_j)\) — короткая генерация;
- \(G_{\mathrm{ref}}(z_j)\) — сохранённая длинная генерация;
- \(m\) — число изображений.

Считать ошибку нужно по исходным числам с плавающей точкой в одинаковой шкале, до преобразования в PNG.

Меньшая MSE означает, что короткий алгоритм приблизился к выбранному длинному результату. **Это ещё не доказательство улучшения FID.** Последний оценивает другую характеристику — близость статистик набора генераций к реальным изображениям.

### 4.4. Простой алгоритм поиска расписания

Для основного опыта достаточно подбирать расписание **для DPM-Solver++ при 19 вызовах модели**.

Предлагаю такой алгоритм:

1. Взять исходную сетку Karras.
2. Выбрать три внутренние опоры примерно в первой четверти, середине и третьей четверти последовательности.
3. Проверить небольшой сдвиг первой опоры в сторону большего шума.
4. Проверить такой же сдвиг в сторону меньшего шума.
5. Сохранить изменение, если оно уменьшает среднюю MSE.
6. Аналогично обработать вторую и третью опоры.
7. Повторить проход с меньшей величиной сдвига.
8. Проверить лучшие варианты на отдельном наборе шумов и зафиксировать результат.

Для аккуратной реализации удобно задавать сдвиги в логарифмической шкале \(\sigma\), а между опорами интерполировать **сдвиги относительно исходной сетки**. Тогда нулевые сдвиги точно воспроизводят исходный вариант.

После каждого изменения нужно проверять:

- допустимость уровней;
- строгий порядок;
- отсутствие повторов после привязки к дискретным меткам;
- сохранение числа узлов.

Три опоры, два направления и три прохода дают не более **18 новых кандидатов плюс исходный вариант**. Такой поиск достаточно мал, чтобы его было легко реализовать, проверить и объяснить на защите.

## 5. Как организовать честное сравнение

### 5.1. Сравнивать число вызовов модели

Нельзя просто выставить всем алгоритмам «20 шагов».

Если расписание содержит \(K\) положительных уровней и завершается переходом к нулю, то:

- DDIM требует \(K\) вызовов;
- многошаговый DPM-Solver++ требует \(K\) вызовов;
- Heun требует \(2K-1\) вызовов.

У Heun второй вызов отсутствует только на последнем переходе. [GitHub](https://github.com/NVlabs/edm/blob/main/generate.py?utm_source=chatgpt.com)

Поэтому предлагаю следующие бюджеты:

| Число вызовов модели, NFE | Положительных уровней DDIM | Положительных уровней DPM-Solver++ | Положительных уровней Heun |
|---:|---:|---:|---:|
| **9** | 9 | 9 | 5 |
| **19** | 19 | 19 | 10 |
| **39** | 39 | 39 | 20 |

Реальные вызовы нужно считать непосредственно вокруг U-Net. Даже при одинаковом NFE время может немного различаться из-за дополнительных операций, поэтому оно измеряется отдельно.

### 5.2. Разделить шумы для подбора и проверки

Предлагаемый размер наборов:

| Назначение | Количество |
|---|---:|
| Подбор расписания | 32 начальных шума |
| Выбор среди лучших вариантов | 64 других шума |
| Итоговое сравнение по MSE | 256 новых шумов |
| Итоговая генерация для FID | 5000 новых шумов на конфигурацию |

Это рабочие размеры для ограниченного бюджета, а не требования курса.

Все наборы должны быть непересекающимися. Для сравниваемых методов используются одинаковые сохранённые начальные массивы с корректным переводом в координаты каждого алгоритма.

После просмотра итогового теста параметры уже не подбираются. Иначе тест перестаёт быть независимой проверкой.

### 5.3. Ограничить число экспериментов

| Серия | Что запускаем | Что выясняем |
|---|---|---|
| Стандартные методы | 3 сэмплера × 2 расписания × 3 бюджета = **18 конфигураций** | Зависимость MSE, времени и визуального качества от алгоритма и сетки |
| Подбор | DPM-Solver++ при NFE 19 | Можно ли улучшить исходное расписание |
| Перенос | Найденное правило сетки в трёх сэмплерах при NFE 19 | Работает ли оно за пределами исходного алгоритма |
| Финальный FID | 3 сэмплера × исходная и найденная сетки = **6 конфигураций** | Как подбор влияет на распределение генераций |
| Анализ участков | Отдельное изменение ранней, средней и поздней опоры | Где перераспределение уровней полезнее |

Для анализа участков три контрольные сетки подбираются заранее, каждая из одной исходной Karras и с одинаковым бюджетом поиска. На итоговых шумах они только оцениваются.

### 5.4. Правильно перенести расписание в Heun

При NFE 19 у DDIM и DPM-Solver++ по 19 положительных узлов, а у Heun — 10.

Поэтому в Heun переносится **правило расположения уровней**: та же функция опорных сдвигов вычисляется для другого количества точек. Буквальное копирование списка из 19 узлов изменило бы вычислительный бюджет.

В отчёте это нужно назвать переносом правила построения сетки.

### 5.5. Аккуратно оценить FID

Практично использовать **clean-fid**. В нём предусмотрены статистики CIFAR-10 и согласованный способ обработки изображений; авторы отдельно показывают влияние изменения размера и квантования на результат метрики. [GitHub](https://github.com/GaParmar/clean-fid?utm_source=chatgpt.com)

Для собственного сравнения можно выбрать:

- реальные изображения — CIFAR-10 test, 10 000;
- сгенерированные — 5000 на конфигурацию;
- одинаковую реализацию и предобработку во всех опытах.

FID на конечной выборке имеет смещение, причём одинаковое количество изображений полностью его не устраняет. Поэтому небольшую разницу на 5000 генераций стоит перепроверить, если на ней строится основной вывод. Такие числа также нельзя напрямую сравнивать с результатами статей, использующих другой протокол. [openaccess.thecvf.com](https://openaccess.thecvf.com/content_CVPR_2020/html/Chong_Effectively_Unbiased_FID_and_Inception_Score_and_Where_to_Find_CVPR_2020_paper.html?utm_source=chatgpt.com)

## 6. Подробный план реализации

### Этап 1. Окружение и первый базовый результат

**Что сделать**

Создать ноутбук в Colab или Kaggle, проверить доступную GPU, установить совместимые версии PyTorch и Diffusers. Загрузить модель и изучить её конфигурацию.

Сначала работать в FP32 с небольшим пакетом. Получить 16–32 изображения готовым алгоритмом, сохранить начальные шумы, настройки и результат. Повторить детерминированную генерацию.

**Результат этапа**

Рабочая генерация, зафиксированные версии зависимостей, понятный формат входа и выхода модели.

### Этап 2. Собственный DDIM

**Что сделать**

Разобрать один переход по формулам. Реализовать вычисление оценки чистого изображения, переход к следующему уровню и завершение генерации.

Сначала использовать штатную сетку `DDIMScheduler`. Проверить один шаг на одинаковых входных тензорах, затем короткую полную траекторию.

Сравнивать численные расхождения, а не только визуальную похожесть картинок.

**Результат этапа**

Собственный DDIM, совпадающий с выбранной библиотечной конфигурацией в пределах объяснимой численной точности.

### Этап 3. Общий адаптер модели и Heun

**Что сделать**

Построить таблицу соответствия времени и уровня шума. Реализовать масштабирование входа и преобразование epsilon-предсказания в оценку чистого изображения.

Затем реализовать предварительный переход Heun, повторный вызов модели, коррекцию и завершающий Euler-переход.

**Результат этапа**

Проверенный Heun с правильными начальными условиями и счётчиком NFE. Модель не вызывается на нулевом уровне шума.

### Этап 4. DPM-Solver++ второго порядка

**Что сделать**

Добавить сохранение предыдущего предсказания, формулу второго порядка для неравномерных интервалов, стартовый переход и завершение.

Перед каждой новой генерацией очищать историю. Согласовать параметры с `DPMSolverMultistepScheduler` и проверить отдельные переходы.

**Результат этапа**

Три собственных алгоритма работают с одной моделью через общий интерфейс.

### Этап 5. Стандартные расписания и единый протокол

**Что сделать**

Реализовать равномерную сетку и Karras с привязкой к исходной таблице модели. Добавить проверки порядка, границ и количества узлов.

Зафиксировать одинаковую обработку предсказаний. Для первого контролируемого сравнения удобно отключить внутренний clipping в DDIM и Heun и thresholding в DPM-Solver++, а окончательное преобразование изображения выполнять одинаково. Если ограничение значений потребуется для устойчивости, его следует вводить единообразно.

**Практическая ловушка:** в просмотренном исходнике `DDIMScheduler.step` следующая временная метка вычисляется через стандартный размер шага. Поэтому простая замена массива `scheduler.timesteps` на произвольный список не обеспечивает нужные переходы. Нерегулярную сетку нужно реализовать через явные пары текущего и следующего узла. [GitHub](https://github.com/huggingface/diffusers/blob/main/src/diffusers/schedulers/scheduling_ddim.py?utm_source=chatgpt.com)

**Результат этапа**

Конфигурации различаются только исследуемым сэмплером и расписанием; остальные условия контролируются.

### Этап 6. Опорные изображения и поиск расписания

**Что сделать**

Подготовить непересекающиеся наборы шумов. Проверить устойчивость длинной генерации и сохранить опорные результаты.

Запустить ограниченный поиск по трём опорам. Для каждого кандидата записывать параметры, MSE, NFE и время. Выбрать финальный вариант по отдельному проверочному набору.

На этой же стадии подготовить контрольные сетки для анализа разных участков траектории.

**Результат этапа**

Исходная и найденная сетки, журнал поиска и все параметры, зафиксированные до итогового теста.

### Этап 7. Итоговые эксперименты

**Что сделать**

Выполнить 18 стандартных конфигураций на отложенных шумах, добавить найденное расписание и его перенос. Оценить заранее подготовленные контрольные сетки.

Получить FID для шести финальных конфигураций. Построить графики и сохранить изображения из одинаковых начальных шумов, включая неудачные случаи.

Время измерять после прогрева, с синхронизацией CUDA и несколькими повторами. Операции GPU асинхронны, поэтому без синхронизации замер может отражать постановку вычислений в очередь. [PyTorch main documentation](https://docs.pytorch.org/docs/main/notes/cuda.html?utm_source=chatgpt.com)

**Результат этапа**

Таблицы и графики, из которых можно непосредственно получить выводы проекта.

### Этап 8. Отчёт и защита

**Что сделать**

Описать постановку, методы, адаптер, проверку с Diffusers, алгоритм поиска и условия экспериментов.

Отдельно объяснить:

- где удалось уменьшить MSE;
- изменился ли FID;
- переносится ли найденное расписание;
- где оно ухудшает результат;
- сколько стоил подбор;
- при каких условиях получены выводы.

Сопоставить комплект материалов с актуальными критериями LMS.

**Результат этапа**

Работа, которую другой человек может воспроизвести по инструкции, а автор — объяснить по собственным функциям и результатам.

## 7. Сколько времени закладывать

При базовом знании PyTorch я бы планировал **примерно 50–80 часов активной работы**. Это моя оценка для предложенного объёма, а не гарантированный срок.

| Работа | Ориентир |
|---|---:|
| Основы диффузии и чтение алгоритмов | 6–10 часов |
| Окружение и базовая генерация | 3–5 часов |
| Собственный DDIM | 4–6 часов |
| Адаптер и Heun | 8–12 часов |
| DPM-Solver++ и общая проверка | 8–12 часов |
| Подбор расписания | 6–10 часов |
| Эксперименты и анализ | 8–12 часов |
| Отчёт и защита | 5–8 часов |

Удобный календарный план — **4–6 недель** регулярной работы:

- первая неделя — основы, запуск модели, DDIM;
- вторая — адаптер, Heun, DPM-Solver++;
- третья — проверки, опорные изображения, поиск расписания;
- четвёртая — итоговые измерения и отчёт;
- оставшееся время — резерв на изучение и исправления.

Время GPU считается отдельно. По предложенной матрице объём генерации составляет порядка **1,1 млн произведений «изображение × вызов модели»**. Это расчёт количества работы, а не замер скорости.

После первого запуска следует измерить производительность на фактической GPU и оценить продолжительность основных серий. Самыми затратными окажутся длинные опорные генерации и изображения для FID.

Бесплатные ресурсы Colab не гарантируют конкретную GPU и постоянные лимиты, поэтому результаты нужно сохранять по мере выполнения, а генерацию организовать с возможностью продолжения после остановки. [research.google.com](https://research.google.com/colaboratory/faq.html?utm_source=chatgpt.com)

## 9. Что читать и с чего начать

Предлагаю такой порядок:

4. [DPM-Solver++](https://arxiv.org/abs/2211.01095) и [его реализация в Diffusers](https://huggingface.co/docs/diffusers/api/schedulers/multistep_dpm_solver) — разобраться с использованием истории.
5. [Clean-FID](https://github.com/GaParmar/clean-fid) — подготовить оценивание до массовой генерации.

**Первое практическое действие — получить 16 изображений готовой моделью и разобрать один DDIM-переход. Следующая контрольная точка — собственный DDIM с численной проверкой.** После этого будет понятна базовая механика проекта, и можно последовательно добавлять Heun, DPM-Solver++ и подбор расписания.
